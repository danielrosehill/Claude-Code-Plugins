# Marketplace Changelog

A record of how the `danielrosehill` Claude Code plugin marketplace has evolved over time. Follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) conventions loosely — entries are grouped by date and marketplace version.

## Unreleased

### Added — 2026-08-05

- **`spec-led-certification` 0.3.0** — 2026-08-08 — adds `create-workspace`, which stands a search up as a **private GitHub repo instantiated from the template repo** rather than only as a local folder. The workflow's premise is that its state outlives the conversation, and a folder on one machine is a weak form of that: a repo survives the laptop, and the git history showing the scorecard committed *before* the research ran is the evidence the whole method rests on — a frozen scorecard nobody can date is a claim about process rather than proof of it. Instantiating the template also carries `skills/`, `agents/` and `docs/` into the new repo, so it explains its own process with no plugin installed, which is the agent-agnostic claim delivered rather than asserted. Verified against a throwaway repo: `gh repo create <name> --template <repo> --private --clone` handles the template-instantiation race internally — the clone arrives complete rather than empty, so no wait loop is needed — and the result is a squashed `Initial commit` with **no upstream link**, which is correct here, because a search in progress should not receive template changes underneath a frozen scorecard. `scaffold-workspace` remains for searches that belong inside an existing repo, where `gh` is unavailable, or where the user wants no remote; `/cert-search` gains `--repo` and `--local` and prefers the repo path, falling back when `gh auth status` fails. Creating the repo is gated behind an explicit confirmation showing the exact command, and the confirmation states what the repo will end up holding — what the user knows, what they can spend, what they are trying to move toward — so a `--public` choice is made knowingly rather than by a default nobody read. Also adds the third leg of the plugin/template/user-data pattern: the user's own defaults for owner, visibility, clone parent and naming live in `~/.claude-plugins/spec-led-certification/config.yaml`, outside both the plugin directory (which `/plugin update` replaces wholesale) and the two public repos, so nobody's defaults are ever committed upstream. `sync-from-template.sh` now takes a `PLUGIN_OWNED_SKILLS` list rather than hardcoding one name, which `--check` had begun reporting as drift.

- **`spec-led-certification` 0.2.0** — 2026-08-08 — splits the workflow into three atomic entry points, because the three situations someone arrives in have different concerns and were previously branches inside one skill. `start-search` is onboarding: it sets expectations before the first question, since being asked about yourself before any option is named is unusual enough to need explaining, and it carries the first-run guardrails — a credential named in the first minute anchors the topic list, the weights and the search, and new users wave away the kill condition that is most of what stops the workflow becoming a machine for justifying a decision already made. `rerun-search` archives the previous run to `runs/<date>/` — scorecard, data and conclusion together, because archiving only the scores makes the diff unreadable the moment a weight changes — and leads its report with a new `changes` section: whether the earlier recommendation still holds, which scores moved and why, what entered or left, and explicitly whether a movement was a real change or a rescoring on better evidence, since conflating those makes the market look more volatile than it is. It re-checks the *excluded* list too, because eligibility gates open as well as close. `update-profile` re-interviews only what changed and stops there — a two-minute correction should not drag an hour of research behind it. The interlock that makes it mean anything is a new `stale` flag on the scorecard, kept deliberately separate from `frozen`: `frozen` is a fact about the past that the pre-research commit evidences, so unsetting it to signal "needs rebuilding" would destroy the record that the method was followed, while `stale` says the criteria need rebuilding before the next survey. `rerun-search` reads it and rebuilds and re-freezes; without it the next run scores a changed person against an unchanged specification and produces a ranking that looks fine and is wrong in a way nothing surfaces. `spec-led-certification` is demoted to a router over the three. `/cert-search` gains `--new`/`--rerun`/`--update` and routes on workspace state when no flag is given; `--refresh` is superseded by `--rerun`. Report renders the `changes` section only when non-empty, so first runs are unaffected.

- **`spec-led-certification`** — 2026-08-08 — choose a professional certification specification-first rather than market-first. The failure it addresses is an ordering one: choosing a credential normally starts from what is on offer, which makes the exam's blueprint your specification by default, and the criteria you would have written get recovered afterwards as reasons for a choice already made. The tell is that the answer is usually the most famous option. So the workflow interviews first — five separate intake skills writing five dated files, because they decay at different rates: what you know is stale in a quarter, how you learn is much the same in five years, and fusing them means the whole profile expires at the rate of its fastest part, which is exactly the cost that stops anyone re-running anything. A re-run re-asks the one file past its `review_after` and confirms the rest. `build-scorecard` then derives weighted, anchored criteria from `profile/` alone and **freezes** them, enforced three ways: every criterion carries a `source` column naming the profile line it came from, the scorecard is committed before research runs, and the `research` subagent receives the frozen card without the intake conversation, so there is no anchor available to bend toward. Hard requirements go to `filters.csv` and **exclude** rather than score down — a requirement that can be outweighed is not one, and scoring eligibility instead of filtering on it is how a credential nobody can sit places third. Research tags every claim `V` vendor-confirmed / `S` secondary / `I` inferred, because this domain has a specific bias in its material: certifying bodies often gate their blueprints, and the ungated sources are mostly selling preparation, which gives them standing reason to run optimistic on both eligibility and value. Reporting is Typst reading `criteria.csv` and `scores.csv` at compile time and computing the totals, ranking and comparison table itself — the `recommend` skill writes prose only, so a revised score cannot leave a stale sentence behind. All state is markdown and CSV in the working directory, never an agent memory store, so the next pass can run with a different assistant. Packaging of the template repo [Spec-Led-Certification](https://github.com/danielrosehill/Spec-Led-Certification), which stays canonical: the nine stage skills, three subagents and workspace files are vendored verbatim by `scripts/sync-from-template.sh`, `--check` reports drift, and only `commands/`, `skills/scaffold-workspace/` and `.claude-plugin/` are owned by the plugin. Listed under Research & Learning.

- **`rtl-email`** — send email in right-to-left scripts (Hebrew, Arabic, Farsi, Urdu) that renders RTL in the recipient's client. Plain-text email carries no direction metadata, so RTL bodies render LTR in many clients — Outlook routinely — and multi-part numbers reorder their separators, corrupting the account and reference numbers a recipient uses to find the file. Ships `dir=rtl` HTML templates (ordinary and formal), `send-rtl-personal-email` and `send-rtl-business-email` inheriting separate saved signature profiles and registers, and `configure-rtl-signatures` for one-time setup under the `$CLAUDE_USER_DATA` resolver. Works with Google Workspace MCP or Resend. Repo: [Claude-RTL-Email](https://github.com/danielrosehill/Claude-RTL-Email).

### Added — 2026-07-30

- **`netek-disconnect`** — cancel Israeli service subscriptions (ניתוק) through [netek.co.il](https://www.netek.co.il/), which relays cancellations to providers on a customer's behalf. 55 providers across eight categories: mobile, landline, internet, TV, international calling, water bars, newspaper subscriptions and credit cards. Four skills — `netek-disconnect` (the flow), `netek-profile` (the user's details, optionally from 1Password), `netek-providers` (provider/service/address lookup), `netek-status` — plus `/netek`. The API is **unofficial and undocumented**; `docs/api-map.md` records what was verified live on 2026-07-30, what is only inferred from the JS bundle, and the recipe for re-deriving it, since Netek ships a new hashed bundle on every deploy. What reading that bundle produced: the wire field names **differ from the form's input names** (`personalID` → `personalId`, and on a business account `contactName` → `fullName` with `companyID` → `personalId`), so a payload built from the visible form is wrong; for mobile and landline the number being cancelled is **appended to the service string** as `טלפון נייד שמספרו 050-1234567` rather than sent as its own field, and omitting it produces a cancellation that does not say which line; the service string is matched literally, so a translated or paraphrased category does not route; provider IDs are non-contiguous and do not match array position; and `GET /p/common/streets` takes the **numeric city code**, returning `[]` with HTTP 200 for a city *name* — an empty result that reads as "no such street" rather than "wrong parameter". Validation mirrors Netek's own validators, including the Israeli ת.ז. check digit and a phone regex that **requires the hyphen** (`050-1234567`), because the server's behaviour on bad input is unknown — testing it means submitting. `POST /p/request` was deliberately never exercised: a success sends a real cancellation, with a real person's ID, to a real company, and there is no unsend; the status and activation endpoints are marked *inferred* for the same reason, since both need a guid only a live submit produces. Consent is structural rather than advisory — `build` and `submit` share one payload builder so what the user approves is byte-identical to what is sent, `submit` refuses without `--confirm`, and **the activation link Netek emails is left for the account holder to click**: the request is inert until then, which is the one step an agent cannot fake and therefore the thing that makes preparing a cancellation safe to automate at all. Netek's `/p/leads/*` endpoints are documented but never called — they pass the user's details to *competing* providers as a sales lead, and someone cancelling a line has not asked to be sold to. There is no Netek account, key or session; every endpoint is unauthenticated, so the optional 1Password integration protects the user's own ת.ז. and card last-4 rather than authenticating anything, and nothing anywhere wants a full card number. Profiles live at `~/.claude-plugins/netek/` rather than the working tree. `scripts/netek.py` is stdlib-only; `refresh_providers.py --check` exits non-zero on catalogue drift. Not yet run end to end against a live submit. Listed under Regional.

- **`netek-disconnect` 0.2.0** — adds `netek-browser-fallback`, a second path to the same form through the Chrome MCP, and states provenance plainly. The two paths fail in opposite conditions, which is the point: `service.netek.co.il` is Netek's own private backend — no developer portal, no documentation, no OpenAPI (`/swagger`, `/api-docs` and the rest all 404), nobody to request access from — so it is owed no stability and can be changed or switched off without notice, while the website is the route Netek actually supports. The fallback matches fields by **visible Hebrew label** (`ת.ז.`, `ישוב`, `רחוב`, `4 ספרות אחרונות של אמצעי המשמש לתשלום`, `שלח`) rather than by selector, because a new hashed bundle ships on every deploy and class names are worthless while labels are stable; it also notes that `ישוב`/`רחוב` are autocompletes that must be *selected* from the dropdown or the postcode never populates, and that the number being cancelled is its own field (`טלפון לניתוק`) in the form where the API folds it into the service string. It triggers on **transport** failures only — HTTP errors, unparseable responses, 404s on endpoints that used to work — never on validation, since a failed ID checksum fails identically in both paths and falling back would only reach the same rejection more slowly. Firing the fallback obliges the operator to record what broke in `docs/api-map.md`, so a one-off repair doesn't silently become a permanent detour. On provenance: the API was mapped by reading the JavaScript Netek serves every visitor plus read-only GETs — nothing bypassed, since nothing is authenticated, and no private traffic captured — and `POST /p/request` remains deliberately unexercised, so its response shape and the status/activation endpoints stay marked *inferred*. Also softens the `/p/leads/*` stance: the `בא לך לשמוע הצעה מחברה אחרת?` checkbox (key `chooseLeadProviders`) solicits competing offers and passes name, phone, city and email to other providers, and cancellation never depends on it — but banning it outright was too paternalistic, since someone leaving a provider is exactly who might want to compare. Now off by default, the user's call either way, and disclosed when turned on.

- **`contact-support`** — *work in progress, concept stage.* Contact a vendor's support desk from a registry of verified contact routes instead of recalled ones. The premise: support routing details are the worst case for model recall — low-salience, changed without announcement, and wrong in a way that costs a support window rather than failing loudly. Verifying one vendor properly demonstrated how badly it fails. **`help@twilio.com` does not exist**; the help-centre article whose entire purpose is explaining how to contact Twilio support carries **no `mailto:` link at all**, because Twilio publishes no general support email. Worse, **`spam@twilio.com` is printed by Twilio and is not what the link points at** — the `mailto:` href behind that link text is `stopspam@twilio.com`, so the wrong address is not a plausible invention but what a correct reading of the visible page produces, and everything downstream of a text scrape inherits it. Hence the two research rules now in the skills: **extract `mailto:` hrefs, never prose**, and **when a help centre is unreadable, read the one it replaced** — `help.twilio.com` is a client-rendered SPA returning nothing but a `<title>` to any fetcher (its `/api/v2/help_center/` path serves the shell, not JSON, so it is not an addressable Zendesk instance), but the `support.twilio.com` Zendesk it superseded *was* server-rendered, article IDs survived the migration, and the Wayback CDX index lists every archived article. Six article bodies read that way, which converted most of the entry from `referenced` to `confirmed`: the plan/channel matrix (**the free Developer plan has no direct Submit-a-Ticket link at all** — the AI Help Center Assistant is its only route; live chat starts at Production, phone at Business, so neither is simply "paid plans"), eleven products that are ticket-only whatever you pay (Studio, Conversations, Video, REST API, Functions, CLI, Event Streams, Sync, Notify, Frontline, NTS), the P1/P2/P3 definitions with P1 defined as production-only, the **default to P3** when unset, Twilio's stated practice of downgrading misfiled P1s (so inflating priority is self-defeating and visible), follow-the-sun 09:00–18:00 hours with per-country holiday calendars across 22 countries — which is what makes "6 business hours" a regional quantity — and the no-login ticket fallback, which is **handled as if no plan is on file** so a paid SLA does not apply to it. Seven skills: `support-lookup`, `support-account`, `support-request`, `support-send`, `support-followup`, `support-add-service`, `support-revalidate`, plus `/contact-support`. Every claim in a service entry is graded `confirmed` / `referenced` / `inferred`, with an `evidence` string **required** for anything confirmed and enforced by `scripts/check_registry.py` — which validates and ages entries but deliberately does **not** test reachability, because a status code is not a verdict: `discord.gg/twilio` returns 301 to an invite the Discord API resolves as `Unknown Invite`, `help.twilio.com` returns 200 with no content, and `support.twilio.com/hc/en-us` returns 403 to fetchers while working in a browser. Nine dead routes recorded. Drafting and sending are separate skills because sending is irreversible, and `not_for` plus `agent_reachable` exist to stop the specific failure of an agent reaching for the easy-but-wrong public channel — publishing the user's problem with an Account SID attached somewhere that cannot solve it. User data lives at `~/.claude-plugins/contact-support/` (accounts, user-authored entries, ticket logs with a `response_due` the follow-up skill runs on) rather than inside the plugin, because `/plugin update` replaces the plugin directory; overrides win over shipped entries, accumulated lists concatenate, and the *older* verification date governs a merged entry so a fresh override cannot make stale channels look trustworthy. Credentials are stored as pointers only — `op://` reference, env var name, vault item title — never values, so no secret enters a draft or transcript. Ships **Twilio only**, deliberately: 14 channels, 9 `known_dead`, 16 gotchas, 90-day revalidation window. Not yet run end to end against a live support desk. Listed under Personal Productivity.

- **`label-printer`** — print labels on a Brother P-touch label printer. Eight MCP tools: `printer_status`, `printer_capabilities`, `preview_label` (renders and returns the image without spending tape), `print_label`, `print_text_label`, `print_asset_label` and `print_storage_label` (inventory templates applying `A-` / `S-` id prefixes), and `print_batch` (up to 50 different labels per run). Four skills: `label-an-asset`, `label-a-storage-unit`, `batch-label-run`, `printer-troubleshooting`. The MCP renders with PIL + `qrcode` at 12 px/mm and posts the bitmap to the [ptouch-cube-print-bridge](https://github.com/danielrosehill/ptouch-cube-print-bridge) HTTP bridge, which drives `ptouch-print` over USB — the plugin is useless without that bridge deployed, and `PRINT_BRIDGE_URL` defaults to localhost rather than any real address. Tape narrower than 18 mm drops the second line. Also documents what the Linux driver *cannot* do: `ptouch-print` v1.8 is print-only, so auto power-off is unreachable from Linux by every route (driver, Bluetooth, mobile apps, Wine) and is a one-time NVRAM change in Brother's Windows/macOS Printer Setting Tool — `printer_capabilities` returns this so the agent stops offering a setting it can't reach. Pins `mcp>=1.10,<2`, since mcp 2.0 renamed `mcp.server.fastmcp` to `mcp.server.mcpserver`. Verified end to end against a PT-P710BT on 24 mm tape. Listed under Hardware & Maker.

- **`israel-opening-hours` 0.2.0** — bundles 56 Israeli locations in `data/israel-cities.json`, generated from the GeoNames Israel dump and verified against Hebcal, replacing a hand-written 24-city alias list. Addressed by **geonameid, never lat/lon**: Hebcal attaches a candle-lighting custom to each known location and silently drops it for bare coordinates — Jerusalem by geonameid lights 40 min before sunset (18:56 on 2026-07-31), the identical coordinates by lat/lon give 19:16, a 20-minute error on every derived time. Rehovot, Safed, Karmiel, Akko, Afula, Givatayim, Kiryat Gat, Nahariya, Umm el Fahm and Modi'in Illit now resolve where Hebcal's `IL-` identifiers rejected them. - **`freight-vol-calculator`** — freight volume arithmetic from a product's external dimensions. Five skills: `size-a-shipment` (orchestrator — establishes carton dimensions vs product dimensions, quantity, origin, whether the product nests, and any rate held, then writes a brief naming the binding constraint and the one thing worth changing), `pallet-quantity` (layer pattern, layers, build height, deck utilisation across 11 standards), `container-load` (palletised *and* floor-loaded figures for every unit, since they routinely differ by 30–60% and that gap is the decision), `packing-options` (enumerates `nx × ny × nz` arrangements of each pack count over each unit orientation, adds the box wall, drops anything past handling limits, prices survivors out to a pallet and a container), `freight-cost` (divides the user's rate by the computed load: FCL, per-CBM groupage with minimum billed volume, per-pallet, per-kg chargeable weight with sea/air/road/courier divisors, quantity price breaks, CIF-based duty, LCL–FCL crossover quantity). Engine is `scripts/freight.py`, stdlib only, no network, no API keys, `--json` on every subcommand and `--dim-units mm|cm|m|in` on input. Layer packing is exact guillotine-lane recursion plus a bounded five-block pinwheel search, because lanes cannot express a rotated pattern and 600 × 400 on an 1100 × 1100 Asia pallet fits 4 as a pinwheel against 3 in lanes. Pinwheels are **disabled for pallets going into a container**: a mixed floor plan fits 10 Chinese 1200 × 1000 in a 20 ft against 9, which is valid geometry but needs a placement diagram and a loading order, so it is reported as a note rather than claimed as the figure. Nesting is modelled as a stack pitch (`--nesting 0.75` = each further unit adds a quarter of its height) since an empty-crate load is ~3× a stacked one. Payload caps apply after geometry, pallet tare included, so a dense load says "the container ships part empty" instead of quoting unreachable volume. Billed volume follows what is actually paid for: pallet footprint × built height with the last pallet costed short, or a unit's share of its column when loose. Buffers are explicit and overridable — 50 mm loading clearance along the length, 5% derate on floor-loaded figures, zero on palletised ones because that geometry is already exact. Reference data in `data/*.csv` with a `provenance` column (specified / typical / indicative): 11 pallet standards and 7 transport units including the 13.6 m curtainsider for the loading-metre basis; add a row and every subcommand picks it up. `freight.py selftest` asserts 37 checks anchored on published trade figures — 11/25/23 EUR-1 per 20 ft / 40 ft / 40 ft with clearance, 33 per curtainsider, 9 Chinese 1200 × 1000 per 20 ft, 10 Australian 1165 × 1165 — and validates every returned layout for overlap and overhang. Documents where it can be beaten: the layer count is a heuristic lower bound, mixed-SKU loads, axle weights, VGM and stacking strength are out of scope, and a container door clears ~2280 mm where the internal height is 2393 mm, so a pallet built to the ceiling does not go in. Listed under Marketing & Shopping.

- **`freight-vol-calculator` 1.1.0** — adds the retrieval half, which the first release left as four hand-typed numbers. New `listing-dimensions` skill: a fetch escalation ladder (WebFetch → fetch-to-markdown MCP → browser MCP → curl, because the packaging block on Alibaba, AliExpress, Amazon and 1688 only exists after JavaScript runs), where the figures actually live per platform — Alibaba's `Packaging and delivery` block and the `Selling Units` field that decides whether `Single package size` means a retail box or a master carton; 1688's 外箱尺寸 / 装箱数 / 毛重 / 净重; Amazon's `Product Dimensions` vs `Package Dimensions` and third-party sellers pasting one into both — and the rule that a missing dimension is a question for the supplier, never an interpolation, with RFQ wording that asks for the loading plan rather than the pallet size. Asking the user to paste the block is documented as a normal outcome on these sites. New `verify` subcommand cross-checks the figures before anything is computed on them: **the claimed pack count against what the carton cavity physically holds**, run through the same packer as the rest of the plugin (12-per-carton against a carton that holds 8 is invisible to careful reading); stated CBM against the dimensions, naming a litres/m³ mix-up when the ratio says so; gross vs net; density with the per-container payload/cube thresholds; units-of-measure absurdities in both directions; packing efficiency, flagging both a carton that is over half air and one so tight it must be the internal cavity; and deck fit, suggesting the ISO 3394 module **nearest in area** rather than the one with the most pieces, since nobody repacks a 550 mm carton into a 200 × 150 one. Each dimension carries its own unit flag (`--dim-units`, `--unit-dim-units`) — a product quoted in millimetres against a carton in centimetres is the commonest listing error and now reports itself instead of silently scaling by 10. Also **corrects a claim in the 1.0.0 docs**: "weight binds above ~250 kg/m³" was a rule of thumb; the real threshold is payload over cube and varies 3× across the fleet — 267 for a 13.6 m curtainsider, 347 for a 40 ft HC, 849 for a 20 ft GP — so the same cargo can be weight-limited in a 40 and volume-limited in a 20, which is why dense goods ship in 20 ft boxes. Two limits of `verify` documented rather than hidden: the pack-fit check assumes a plain stack so nesting goods trip it, and internal↔external conversion assumes a uniform wall where real crates taper and vendors measure the cavity at different heights (~10% spread in litres on the same mould). `selftest` 37 → 45 checks.

- **`stack-evaluator`** — review a project's **stack** rather than its code. Code review answers whether the code you wrote is good; it cannot tell you the runtime went EOL last April, that a read-heavy API has no cache at any layer, that nothing backs up the database, or that a broker is running for forty events a day. Those are properties of the component list, and the component list is not in any file a code reviewer reads. Six skills: `stack-inventory` (reads manifests, lockfiles, compose files, CI definitions and infra declarations — never application logic — and records the result), `stack-currency` (latest stable per registry, EOL via endoflife.date, deprecation, abandonment, and the successor project where one is named), `stack-gaps` (what should be here and is not), `stack-fitness` (redundancy, over- and under-engineering, orphaned dependencies, ghost services, expired rationale), `stack-proposal` (target state, sequenced work items, execution brief), `stack-diff` (what changed since the last run). `/stack-eval` runs the sequence. The stack is described against a **fixed list of ~50 slots** rather than freehand, because a freehand description only ever lists what exists whereas a slot list also shows what does not — absence is the finding this plugin exists to surface. Expectations are **archetype-relative**: a static site needs no queue, an authenticated API with no rate limiting is real, and the archetype (`web-app` / `api-service` / `data-pipeline` / `mcp-server` / `homelab-service` / …) is recorded so a *changed* archetype is itself flagged. **Caching is asked about explicitly at all five layers** — edge/CDN, HTTP response, application, data access, client — separately from the archetype table, since it is the slot most often silently absent; but it is only reported as a gap where there is evidence of something worth caching (repeated identical queries, a paid API in a hot path, idempotent LLM inference with no memoization), because adding a cache to an unloaded system buys a new failure mode and a new consistency problem with nothing. Recommendations are right-sized to the project, not to a reference architecture: Postgres `SELECT … FOR UPDATE SKIP LOCKED` before Kafka, an in-process TTL map before Redis, one compose file before Kubernetes, with the heavier option noted as the upgrade path and the signal that would justify it. Being behind is **not** automatically a defect — a supported component two minors back gets a passing grade and one line; findings are reserved for past-EOL, EOL within 12 months, deprecated-with-successor, abandoned, unpatched, or actually blocking something. State persists in the evaluated repo at `docs/stack/stack.json`, which carries three things between runs and is the reason a second evaluation is worth more than a repeat of the first: **settled decisions** (a slot marked `intentionally-absent` with a reason and a date is never re-raised), **finding age** (`first_seen` is never reset, so something open across four runs reads as chronic rather than new), and **rejections**. `stack-diff` also re-checks whether stated reasons have quietly expired — "no production data yet" against a repo that has since grown a deploy target. Evaluation and execution stay separate: nothing in the plugin changes a stack, and the `execution-brief-<date>.md` it hands off copies its work items in rather than referencing them, authorises exactly what it lists, and requires a verification step and rollback path per item — so an implementing agent does not read "stack review" as licence to modernize everything it sees. Not a code reviewer, security scanner, vulnerability database or profiler. Listed under Repo Scaffolding & Retrofitting.

### Pattern notes

The target pattern for every workspace-oriented plugin:

```
<plugin>/
  .claude-plugin/plugin.json
  commands/               # globally available domain primitives
  agents/
  skills/new-workspace/   # provisions a scaffold from template/
  template/               # data scaffold (no .claude/ tree)
    <variant>/
```

Workspace data lives where the user provisions it. Plugin updates never touch user data.
