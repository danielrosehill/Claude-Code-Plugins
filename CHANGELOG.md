# Marketplace Changelog

A record of how the `danielrosehill` Claude Code plugin marketplace has evolved over time. Follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) conventions loosely — entries are grouped by date and marketplace version.

## Unreleased

### Changed — 2026-08-19

- **Every description rewritten for the 59-character window the `/plugin` browser actually shows.** The browse list truncates each description with `Yi(entry.description, 60)` — 59 characters plus an ellipsis — and its search matches only `name`, `displayName`, `description` and `marketplaceName`. `tags` is read for one thing, `tags.includes("community-managed")`, and nothing else. Verified by disassembling the Claude Code v2.1.236 bundle, not from the docs, which list the fields a manifest may contain without saying which are ever surfaced.

  All 146 descriptions were over the limit — shortest 87 characters, median 228, longest 1166 — so every one was being cut. 47 of them opened with the literal string `Claude Code plugin: `, spending 20 of the 59 visible characters, a third of the budget, on a phrase shared by every entry in a Claude Code plugin browser. A further 23 spent 11 more on `workflow — `. Both are now gone; the full text still renders in the detail pane, so nothing was lost, it was only moved behind the fold.

  The browse list reads the **marketplace entry**, not each plugin's own `plugin.json` and not the GitHub repo description — at browse time nothing has been cloned, so this manifest is the only text Claude Code has. That makes it the only place worth editing.

- **`displayName` and `category` added to all 146 entries.** `displayName` is searched and rendered by the browser and was absent everywhere; the values were harvested from the README's own `#### ` headings, which had held them all along in a form nothing could read. `category` is accepted and validates but Claude Code never reads it — it is here solely as input to the catalogue generator, and is recorded as such in `CLAUDE.md` so it is not mistaken for a user-facing field later.

- **`README.md` and `docs/categories/` are now generated** by `scripts/generate-catalogue.py` from the manifest. The README's plugin listing went from 1,795 lines to a single 18-row category table, with full descriptions and per-plugin install commands on one page per category. Previously `/sync-readme` rebuilt the listing by hand and derived grouping from "the first tag, or existing README sections — use your judgment", which is what let the two drift apart: seven registered plugins (`procurement-tools`, `claude-md-tester`, `style-switcher`, `claude-pa`, `claude-document-nudge`, `Easy-Effects-Manager`, `unofficial-mcp-builder`) had no README entry at all, and a stale `purchasing` slug pointed at a plugin that had been renamed. `/sync-readme` and `/check-readme-drift` now drive the generator instead of editing prose.

### Added — 2026-08-19

- **`breakout-claude` 0.1.0 and `obd-diagnostics` 0.1.0 registered.** Both had shipped as public repos — 12 and 16 August respectively — and were in no marketplace, so they were public and undiscoverable. Found by auditing the 200 most recently created repos for an actual `.claude-plugin/plugin.json` rather than filtering on repo name, which would have missed the several plugins whose names do not contain "plugin".

  Both are marked WIP in their own manifests and are listed at the versions those manifests carry, rather than at a catalogue version maintained separately from them.

  The same audit found `uline` private and unregistered anywhere, which is its intended state, and confirmed that `storrs-user-education`, `dsrholdings-accounting`, `dsrholdings-rfq`, `geo-egress` and `gh-ops` are private and correctly registered in the private marketplace rather than missing from this one. `grainger` and `israel-phonebook-manager` remain public and deliberately unregistered.

- **`book-writing` 1.0.0** — writing a full-length reference or instructional book with teams of subagents. Twelve agents across seven stages: definition (`brief-recorder`, `spec-interviewer`, `spec-writer`), planning (`voice-designer`, `outline-architect`), research, parallel chapter drafting, review (`proofreader`, `voice-auditor`, `continuity-auditor`), graphics (`graphics-director`, `figure-maker`) and publication.

  The architecture answers one constraint: **quality degrades long before a context window fills**, so no agent is ever handed the whole book. A single agent carrying a manuscript restates what it said earlier, drifts in register, echoes its own chapter openings, and produces text that is locally fluent and globally empty — failures of long-range coherence that cannot be fixed by trying harder.

  The cost of removing shared context is that agents cannot stay consistent by reading each other, so **consistency is carried by documents instead**: a style guide written to be checkable rather than aspirational, one brief per chapter, and a continuity ledger recording every term, claim, running example and promise the book has established. That trade is the whole pattern.

  Three rules do most of the work, and each prevents a specific observed failure. **Recording and interviewing are separate agents** — an agent that records and questions in one turn leads the witness, and the user's original framing is unrecoverable once paraphrased. **Writers never read other chapters' drafts**, because text in context is text to imitate: a writer that has read chapter three reuses its transitions, borrows its examples and inherits whatever drift it had already accumulated. And **two chapters drawing on the same source do not draft concurrently** — two agents given the same source describe it differently and both descriptions ship, which no per-chapter reviewer will catch.

  Authorship only. Trim, gutter, spine, cover wrap and pre-flight hand off to `kdp-publishing`, which builds the cover last from the interior's measured extent rather than from an estimated page count. Both plugins state the division in both directions: that one does not write your book, this one does not typeset it.

  Each book lives in its own repo instantiated from [`Claude-Book-Workspace-Template`](https://github.com/danielrosehill/Claude-Book-Workspace-Template), which works standalone — `scripts/book.py` is stdlib-only, so `status`, `lint` and `assemble` run with the plugin uninstalled, because a book outlives a plugin version. The pattern is specified at [`Agentic-Book-Writing`](https://github.com/danielrosehill/Agentic-Book-Writing), whose `SPEC.md` is the source of truth; the plugin is an implementation and is wrong where the two disagree.

- **`kdp-publishing` added to the README.** It had been registered in `marketplace.json` since 1.0.0 but was missing from the catalogue README entirely, so it was installable but not discoverable by anyone reading the repo. Both it and `book-writing` now sit under Publishing & CMS.


### Changed — 2026-08-17

- **`amazon-us` → `amazon`, 1.1.0 → 2.0.0, breaking.** Every `/amazon-us:*` command is now `/amazon:*`, and the repo moved from `Claude-Amazon-US-Plugin` to `Claude-Amazon-Plugin`. The plugin was scoped to amazon.com and had no business being: Amazon is roughly twenty separate storefronts with separate catalogues, separate facet grammars and separate currencies, and the same ten-character ASIN can be a live listing on `amazon.co.uk`, a different product on `amazon.com` and nothing at all on `amazon.de`. The machinery is now region-neutral and the region is data — `profiles/amazon-marketplaces.json` carries domain, currency, symbol, postcode label and locale for twenty storefronts plus a `no_local_marketplace` block for destinations served as export markets rather than by a storefront of their own. Only `amazon-us` has a verified facet profile; the others are marked `null` rather than filled with the US node ids, because a US facet applied to another domain does not error, it just filters to something else and returns a clean-looking wrong answer.

  Note the two namespaces this created, which a blanket rename would have collapsed: the **plugin** is `amazon`, while `amazon-us` survives everywhere it means the US **storefront** — the marketplace id, `profiles/amazon-us.json`, and the scoping of which knowledge was verified where. The plugin data directory moved from `claude-plugins/amazon-us/` to `claude-plugins/amazon/`; nothing existed at the old path, so there was nothing to migrate.

  De-regioning surfaced two live bugs. The price extractor was `\$[\d,.]+`, which is USD-only: it returned `null` on every non-US storefront, and also on amazon.com itself whenever the request egressed from Israel and the page rendered ILS. It now matches any currency and validates the result, because Amazon's `a-offscreen` span is a general screen-reader element that also carries "4.5 out of 5 stars". And `probe` used a hardcoded US ASIN, which on another storefront 404s into a page small enough that the bot-wall check calls it walled — reporting a working route as blocked; it now refuses to guess a probe ASIN rather than inventing a verdict.

- **`amazon` gains a user config layer.** Delivery addresses and per-marketplace preferences are read from a user directory outside the repo, found by search order (`$AMAZON_PLUGIN_CONFIG`, then `<user-data-root>/marketplaces/`, then `<user-data-root>/procurement-tools/`) rather than from a hardcoded path. It **adopts the `addresses.yaml` and `marketplaces.yaml` that `procurement-tools` already owns** instead of forking them — a delivery address is not Amazon-specific knowledge, and two copies of one is how a delivery date gets quoted for somewhere the user no longer lives. `scripts/user_config.py resolve <address>` returns the storefront, listing currency, postcode, egress country and facet profile for a destination, and flags the cases where the listed price is not the landed price. Config intake splits in two: `/procurement-tools:shop-setup` interviews for what no account knows, and the new `amazon-account-import` skill reads the address book, default ship-to and Prime state out of a signed-in session, read-only and same-origin, writing no payment data. Also new: `amazon-marketplace-config` and `amazon-open-asin`.

- **`purchasing` → `procurement-tools`, 1.2.0 → 2.0.0, breaking.** The plugin name and therefore the whole command namespace changed: every `/purchasing:*` command is now `/procurement-tools:*`, across all 35 commands and the three variant families (`mkt-*`, `rig-*`, `rec-*`). The rename exists to make the split with `shopping` legible from the name alone. The two plugins were never distinguished by *what kind of thing* you are buying, which is what the old pair of names implied; they are distinguished by whether the question is about the **process** (what is this thing, what must it do, which candidate wins) or about a **place** (who stocks it, at what price, in what currency, under whose tax treatment). `procurement-tools` is marketplace-agnostic by construction and `shopping` is marketplace-specific by construction, and both READMEs now open with a "Which plugin do I want?" table pointing at each other rather than leaving the boundary implied.

  Two migration consequences, neither of which announces itself. The **plugin data directory moved** from `~/.local/share/claude-plugins/purchasing/` to `~/.local/share/claude-plugins/procurement-tools/`, because the path is derived from the plugin name; `marketplaces.yaml` and `addresses.yaml` live there and a missed move reads as an unconfigured price scanner rather than as an error. And `scripts/price_scan.py` resolves that path itself in three fallback branches (`CLAUDE_USER_DATA`, `XDG_DATA_HOME`, `~/.local/share`), so the rename touched Python string literals, not just documentation.

  Cross-plugin references updated in `amazon-us` (README) and `workspace-foundational` (`find-template` skill, the discoverability catalogue). Note that `research-space` also has a workspace variant called `purchasing` — that is a different thing and deliberately unchanged.

- **`shopping` catalogue entry corrected** — the marketplace listed 1.0.0 against a plugin that has shipped 2.0.0 since the `amazon-us` split, and `purchasing` was listed at 1.0.0 against a shipped 1.2.0. Both were stale because the marketplace `version` field is maintained separately from each plugin's own `plugin.json` and nothing reconciles them. `shopping`'s `plugin.json` also carried a `repository` field pointing at `danielrosehill/shopping-plugin` while the actual remote is `danielrosehill/Claude-Shopping-Plugin`; corrected to match the remote.

### Added — 2026-08-17

- **`procurement-tools:define-spec`** — the step before searching, for when you know roughly what you want but not what it is called, and therefore cannot search for it at all. Takes a freeform description, a **photograph**, a close-but-wrong listing, or a part number, and emits two artefacts rather than one: `spec.md`, a vendor-neutral capability specification, and `search-terms.md`, the search vocabulary. The second is the point. A specification you cannot search with is half a deliverable, and the gap between "I want the clamp thing that holds a mic arm" and the string that actually returns it is where most of the time goes.

  The vocabulary is grouped by **register** — canonical/trade name, consumer, industrial/trade, technical spec-code, regional and language variants — because register, not phrasing, is what decides which half of the market a search reaches. The same object has a consumer name and a trade name that return different catalogues at different prices, and the trade term is usually not the one the user said. Each term carries what it skews toward, which marketplaces it works on, and what noise to expect, so an annotation like *"this one will target more industrial products"* is a first-class output rather than an aside. A **decoy terms** section records strings that look correct and return the wrong thing, with what each actually returns; in practice it saves more time than the positive terms do.

  Two design constraints worth recording. Photographs cause systematic **over-specification** — users promote incidental attributes of the example they photographed (colour, housing shape, brand) to essential, and every one so promoted silently excludes a segment of the market, so the command forces an explicit essential/incidental split before writing. And where the identification is genuinely uncertain the command generates terms for *both* candidate identifications instead of committing, because a wrong canonical name poisons every term downstream and does so invisibly — the searches still return results, just the wrong ones. Ships a `search-terms.md` template in the `general-purchasing` variant and a bare `search-terms.txt` for pasting into a search box.

### Added — 2026-08-16

- **`amazon-us`** — 2026-08-16 — Amazon.com marketplace research, split out of `shopping` into its own plugin. Amazon is the case where "the fetch returned something" and "the fetch worked" come apart, and every one of its failure modes renders as a confident, well-formatted, wrong answer rather than as an error. `WebFetch` cannot reach amazon.com at all — HTTP 500 on `/dp/`, 503 on `/s?k=`, consistently rather than transiently. The bot wall answers with **HTTP 200 and a captcha body**, so a check written against the status code reports success while holding a challenge page; `scripts/amazon_fetch.py` tests the body instead, treating anything under 20 KB as walled against a real page's 400–500 KB. The sharpest trap is the delivery date: Amazon geolocates an anonymous request by IP and renders a promise for wherever that IP lands, so the same fetch run from the user's own machine and from a cloud host or a VPN exit in another city produces two equally plausible dates for two different places, with nothing on the page distinguishing them. Every listing result therefore carries `ship_to`, and `--expect-zip` turns a mismatch into an explicit warning instead of a silent wrong answer. Related and non-obvious: the ZIP cannot be recovered by regexing for five digits, because Amazon's own asset filenames collide with real ZIPs — `01890+Vwk8L.css` reads as Winchester MA on every product page. And the anonymous date is the *non-Prime* date, the free-shipping-over-$35 promise; measured across one seven-ASIN shortlist the signed-in Prime session was four days earlier on five of them, so the anonymous figure is quoted as a worst case and the browser is used when arrival timing decides a purchase. Six skills across two tiers — anonymous and stateless (`amazon-fetch-route`, `amazon-shortlist`, `amazon-listing-check`) and signed-in browser for the fields only a session renders (`amazon-delivery-check`, `amazon-search`, `brand-scrub`) — with each tier's descriptions written to say when to use the *other* one, since two skills competing to match the same request is the failure this split exists to fix. Three commands, and `profiles/amazon-us.json` holding everything volatile so an Amazon change edits one file. Two further traps are documented because both silently drop products: browser delivery filters are **sticky across searches**, so a fresh URL with no `rh=` at all still comes back filtered with nothing but the left rail saying so, and the delivery-speed facets are mutually exclusive rather than combinable. Ships no address, account or credentials; asks for a ZIP rather than assuming one; the browser skill is read-only and does not click controls, after a plain navigate in a signed-in session once landed on an order-cancellation page. Repo: [Claude-Amazon-US-Plugin](https://github.com/danielrosehill/Claude-Amazon-US-Plugin). Listed under Marketing & Shopping.

- **`travel-packing`** — 2026-08-16 — making optimal use of a baggage allowance on a multi-carrier international itinerary. The problem is not "what should I bring"; it is that several flights on different carriers each publish a different allowance for a fare brand most travellers cannot name, and the number that actually governs the bags is the tightest one on the route — which nobody works out at 05:00 on the day of the flight. Three design decisions carry the plugin. **Every allowance figure is sourced**: a URL, the sentence it was read in, the fetch date, and a `confidence` of `confirmed` / `inferred` / `assumed`, with the unconfirmed ones staying visibly flagged all the way into the printed document. Not pedantry — baggage allowances are among the most-copied and least-maintained numbers on the web, and an out-of-date aggregator table is indistinguishable from current policy right up until the desk, so a number with no source is treated as a different kind of object rather than as a weaker one. The best source is not the carrier's public baggage page at all but the manage-booking page for the actual ticket, which usually means asking the user to open it and paste what it says; the skill treats that as the highest-quality outcome rather than as a fallback. **It packs to the binding limit** — the tightest per-segment limit across the ticket, recording which segment set it and what the looser limits were — deliberately spending capacity to remove the failure where a bag is legal for the leg that was researched and illegal for the one that was not. And **measured weight beats itemised weight**: nobody weighs every sock, so `reconcile.py` reports the gap between the scale reading and the sum of the inventory in kilograms rather than distributing it silently across estimates, and both rendered documents recompute headroom and status against a scale reading wherever one is heavier than the projection — so a bag can read `OVER` in the PDF while `plan.yaml` still says `tight`, which is the conservative view and is intended. A required `system` field forces the piece-concept-vs-weight-concept determination up front, because splitting a load across two bags either doubles the allowance or buys nothing at all depending on which the carrier uses, and every downstream recommendation inverts with it. Nine skills: `new-workspace`, `itinerary-intake` (which asks for the booking document before asking questions, since it carries the fare brand, the operating carrier and the ticket grouping — the fields that decide the allowance and the ones nobody remembers), `baggage-policy-research`, `packing-inventory`, `weigh-bags`, `pack-plan`, `overage-options`, `leave-behind` and `packing-docs`. Four scripts, no solver dependency: `pack_solver.py` (greedy most-constrained-first seed plus a bounded local search, seeded and deterministic — a packing list that reshuffles between runs cannot be followed, because the things in it are already in cubes), `reconcile.py` (which suggests a scale bias only when every bag shows a same-signed residual of similar size, the signature of a miscalibrated scale rather than of missing items, and never writes it), `validate.py` (schema plus cross-file referential checks) and `render_markdown.py`. The `tight` band is 1.5 kg wide on purpose: home and airport scales routinely disagree by a few hundred grams, and reporting a bag 400 g under its limit as a pass is exactly the proxy-signal error the plugin exists to avoid. The leave-behind ranking divides an *effective* cost — replacement cost at the destination where that is possible, full value where it is not, infinite for essentials — by the kilograms saved, so a 900 g bottle of shampoo replaceable for $4 correctly outranks a 200 g charger worth $60, which no weight-only ordering can reach. Two documents render straight from the workspace YAML with no hand transcription, as PDF via Typst and as Markdown: a one-page counter card, whose real job is to let a traveller check a claim at the desk against the carrier's own published sentence, and a per-bag packing list grouped by cube with tick boxes. Delivery is local, email, cloud storage, or a commit into a static-site repo — where `push` defaults to false and is confirmed separately each time, since a repo wired to a host builds on push, a private repo is not a private site, and this particular document names the dates a home will be empty and lists what is worth taking from it. Deliberately omitted: no volumetric packing model (volume matters, but weight is what gets charged, and per-item dimensions are not data anyone will enter) and no bundled airline allowance database (a cached table would go stale silently and would then be worse than nothing, because it would look like a source). Repo: [Claude-Travel-Packing-Assistant-Plugin](https://github.com/danielrosehill/Claude-Travel-Packing-Assistant-Plugin). Listed under Personal Productivity.

### Changed — 2026-08-16

- **`shopping` 1.0.0 → 2.0.0, breaking** — `amazon-search`, `brand-scrub`, `profiles/amazon-us.json` and `examples/brands.example.json` were removed and now live in the new `amazon-us` plugin. Installing `amazon-us` restores them. The marketplace pattern is inverted by this change: `shopping/profiles/README.md` previously stated it outright — *"Deliberately not one plugin per marketplace. Profiles are data files here; adding a marketplace is adding a file, not a repo"* — and that file is now rewritten to record why it reversed rather than being quietly deleted. Three things broke the original design once the Amazon material grew to two skills, two tested extractors and a 300-line profile. **Versioning**: Amazon changes its facet IDs on its own schedule, so every Amazon fix had to ship as a `shopping` release. **Install weight**: a user who wants Israeli retail discovery has no use for Amazon extraction contracts, and the reverse. **Skill collision**: marketplace skills and general shopping skills compete to match the same user requests, and the model chooses between them with nothing to go on — which is also why the migrated `amazon-search` was rescoped on the way in to say explicitly that `amazon-shortlist` is the starting point and it is for signed-in-only fields. In place of the removed skills, `shopping` gains **`marketplace-plugins`**, the roster: which marketplaces have dedicated plugins, what each covers, how to install, and an instruction to decline rather than improvise when a marketplace has none. It lists `amazon-us` and `aliexpress-israel-skills` today and names Newegg as an underived candidate; `profiles/newegg-us.json` stays behind, still flagged `PLACEHOLDER — NOT YET DERIVED`. Kept deliberately in one place: `purchasing`'s companion skill was renamed `marketplace-plugins` → `marketplace-handoff` and cut back to the boundary rule alone, linking to this roster rather than restating it, since two copies of the same table go stale independently and then contradict each other.

- **`purchasing`** — gains `marketplace-handoff`, the rule for when a purchasing question has stopped being about the product and become a question about one marketplace, with the test being whether the answer would change if the same product were sold somewhere else. Carries no roster by design; see above.

- **Privacy fix** — the `profiles/amazon-us.json` removed from `shopping` contained the author's name and home ZIP in five places (`verified_how`, two caveat strings, a delivery-shape note and a recipe rationale). Those were publicly readable in the `shopping` repo. They are scrubbed in the copy that landed in `amazon-us`, and removing the file from `shopping` retires the exposure going forward, though it remains in that repo's git history.

- **`label-printer`** — 1.0.0 → 1.1.0 — grows from a single-printer P-touch plugin into a multi-printer, multi-backend one, and gains a path that works with nothing deployed. Previously every skill went through the bundled MCP server, which in turn required a USB print bridge running on the host the printer was wired to; that made the plugin useless to anyone who had not first stood up the bridge, and it only ever addressed one hard-coded P-touch. The new `scripts/` layer is standalone: `labelctl.py` discovers printers, keeps a registry and looks up media, and `render.py` renders with Pillow and dispatches to `brother_ql` (network or USB), `ptouch-print` or CUPS. The MCP path remains for setups already built around it, and the four original skills still use it. Five new skills — `profile-printers`, `print-label`, `qr-labels`, `label-templates`, `install-drivers` — plus a `/label` router. **Discovery is mDNS-based**, and that is the load-bearing decision: a networked label printer is frequently not a CUPS queue at all (the QL-810W this was verified against answers on `:9100` and is absent from `lpstat` entirely), while `brother_ql discover` walks USB only and in 0.9.4 raises `NotImplementedError` unless `-b` precedes the subcommand — so anything that discovers by asking CUPS or by asking `brother_ql` reports an empty network next to a working printer. **Preview is a pure-Pillow path that never opens a socket**, because `brother_ql print` converts and transmits in one step, has no dry-run flag, and `--no-cut` suppresses the cutter rather than the print; this was established by printing a label while trying not to. Storage follows the established split — the printer registry is machine-local in `~/.claude-plugins/label-printer/` since it holds LAN addresses true on one network, while templates are user content under a data root resolved by `scripts/paths.sh`, which adopts an existing root rather than starting a second one and refuses any path under `~/.claude`. Media is a bundled catalogue of DK and TZe product codes mapped to pixel geometry, so the canvas comes from whichever roll is recorded as loaded; continuous rolls grow to fit the text and cap at 90 mm, die-cut labels are fixed length and shrink the type instead. Family mismatches are refused at both the registry and the render override, since TZe tape in a QL is not an error the printer can report — it is a wrongly-sized label. Zebra and DYMO are recognised at discovery and registered, but printing to them exits with an explicit message rather than attempting anything; `docs/backends.md` sketches what a ZPL backend would involve and records the findings that cost time, including that reachability on `:9100` says nothing about whether the roll has run out. Verified end to end against a Brother QL-810W on 2026-08-16. Repo: [label-printer-plugin](https://github.com/danielrosehill/label-printer-plugin).

### Added — 2026-08-14

- **`personal-context`** — 2026-08-14 — a persistent background context layer about the user, held as plain markdown files the user owns. The problem it addresses is a consequence of scoping workspaces narrowly, which is otherwise the right thing to do: a workspace bounded to one issue can state what is out of scope, be reviewed in a sitting and be closed, but it starts from nothing, so the person re-explains who they are at the top of every new one, and after the third time they stop opening new ones. The usual fix is a memory feature, and every one of them is vendor-specific, unexportable and unscoped — which for biographical material is the wrong trade, since who is in your life is exactly the category of data you expect to still hold across three tools you have not heard of yet. So it ships as a **contract rather than a feature**: `docs/context-contract.md` specifies the store layout, the entry schema, read and write protocols, backends and an export conformance test, and this plugin is one implementation of it. Two design decisions carry most of the weight. **Scopes**: each entry declares which slices of a life it belongs to and each consumer declares which it may read, so the career workspace does not load the relationship material — and `general` is framed as a budget rather than a default, because a store where most entries are `general` has no scoping at all. **Sensitivity**, kept deliberately separate from scope: `high` entries are never loaded by scope match alone, only when asked for by name, so marking something sensitive costs nothing and hiding it does not require excluding it from a scope where it belongs. `source` and `confidence` are likewise separate fields — something can be stated in an interview as a guess about oneself, or found in a document where it was asserted plainly, and collapsing origin into epistemic status is how an agent's inference becomes a fact about a person two months later. Eight skills: `context-init` (backend, location, scaffold; refuses a public remote with no override), `intake-interview` (seven sectioned, resumable, skippable sections — explicitly not a clinical intake: no instruments, no scoring, no severity questions), `ingest` (journals, exports, old notes, a CV → entries carrying provenance down to the file and date range), `gap-scan` (coverage by type and period, contradictions, staleness, over-broad scopes — then at most five questions, each naming what prompted it, because a gap report that generates thirty gets closed), `context-brief` (the scoped read path, which always says out loud what it loaded), `context-write` (the single place the confirm-before-write rule lives), `context-review` (maintenance that supersedes rather than overwrites — periods get end dates, former clinicians keep their entries, history lines are never deleted) and `context-export` (the portability conformance test: if the bundle cannot be produced and read without the plugin, the store is a memory feature with extra steps). Model-managed memory is prohibited by the spec, including as a fallback when the store is unreachable, because a silent fallback is indistinguishable from a working store right up until the export is empty. Storage follows the established split — machine-local config in `~/.claude-plugins/personal-context/`, user content under a data root — and 0.1.1 makes the second half **resolved rather than assumed**, since a hard-coded default is wrong on any machine where the user already keeps plugin data somewhere else. `scripts/paths.sh` is the single implementation and every skill asks it: `$PERSONAL_CONTEXT_STORE`, then `$CLAUDE_USER_DATA`, then an existing root already on disk (`~/.claude-user-data`, then `${XDG_DATA_HOME:-~/.local/share}/claude-plugins`), then the default — an existing root is **adopted rather than duplicated**, because two roots is how half of somebody's material ends up outside the backup that covers the other half, and the plugin says which rule fired instead of resolving silently. `~/.claude` is a hard error at any depth, with no override, including via an environment variable the user set themselves: that directory is Claude Code's own state rather than the person's content, and a layer whose entire premise is outliving any one tool cannot live inside it. The workspace template's `bootstrap.sh` probes the same order so a workspace lands on the same store with the plugin absent. - **`claude-sops`** — 2026-08-12 — keep personal standard operating procedures as a private library of markdown files the agent reads on demand. The gap it fills sits between two things that already exist and neither of which fits: `CLAUDE.md` is loaded every session, so each procedure added taxes the several hundred conversations that have nothing to do with it, which caps the collection at three or four; and one skill per procedure moves the cost but does not remove it, since every skill's name and description is resident in every session too. Nesting is modelled as a stack pitch (`--nesting 0.75` = each further unit adds a quarter of its height) since an empty-crate load is ~3× a stacked one. Payload caps apply after geometry, pallet tare included, so a dense load says "the container ships part empty" instead of quoting unreachable volume. Billed volume follows what is actually paid for: pallet footprint × built height with the last pallet costed short, or a unit's share of its column when loose. Buffers are explicit and overridable — 50 mm loading clearance along the length, 5% derate on floor-loaded figures, zero on palletised ones because that geometry is already exact. Reference data in `data/*.csv` with a `provenance` column (specified / typical / indicative): 11 pallet standards and 7 transport units including the 13.6 m curtainsider for the loading-metre basis; add a row and every subcommand picks it up. `freight.py selftest` asserts 37 checks anchored on published trade figures — 11/25/23 EUR-1 per 20 ft / 40 ft / 40 ft with clearance, 33 per curtainsider, 9 Chinese 1200 × 1000 per 20 ft, 10 Australian 1165 × 1165 — and validates every returned layout for overlap and overhang. Documents where it can be beaten: the layer count is a heuristic lower bound, mixed-SKU loads, axle weights, VGM and stacking strength are out of scope, and a container door clears ~2280 mm where the internal height is 2393 mm, so a pallet built to the ceiling does not go in. Listed under Marketing & Shopping.

- **`freight-vol-calculator` 1.1.0** — adds the retrieval half, which the first release left as four hand-typed numbers. New `listing-dimensions` skill: a fetch escalation ladder (WebFetch → fetch-to-markdown MCP → browser MCP → curl, because the packaging block on Alibaba, AliExpress, Amazon and 1688 only exists after JavaScript runs), where the figures actually live per platform — Alibaba's `Packaging and delivery` block and the `Selling Units` field that decides whether `Single package size` means a retail box or a master carton; 1688's 外箱尺寸 / 装箱数 / 毛重 / 净重; Amazon's `Product Dimensions` vs `Package Dimensions` and third-party sellers pasting one into both — and the rule that a missing dimension is a question for the supplier, never an interpolation, with RFQ wording that asks for the loading plan rather than the pallet size. Also **corrects a claim in the 1.0.0 docs**: "weight binds above ~250 kg/m³" was a rule of thumb; the real threshold is payload over cube and varies 3× across the fleet — 267 for a 13.6 m curtainsider, 347 for a 40 ft HC, 849 for a 20 ft GP — so the same cargo can be weight-limited in a 40 and volume-limited in a 20, which is why dense goods ship in 20 ft boxes. Two limits of `verify` documented rather than hidden: the pack-fit check assumes a plain stack so nesting goods trip it, and internal↔external conversion assumes a uniform wall where real crates taper and vendors measure the cavity at different heights (~10% spread in litres on the same mould). `selftest` 37 → 45 checks.

- **`stack-evaluator`** — review a project's **stack** rather than its code. Code review answers whether the code you wrote is good; it cannot tell you the runtime went EOL last April, that a read-heavy API has no cache at any layer, that nothing backs up the database, or that a broker is running for forty events a day. Those are properties of the component list, and the component list is not in any file a code reviewer reads. Six skills: `stack-inventory` (reads manifests, lockfiles, compose files, CI definitions and infra declarations — never application logic — and records the result), `stack-currency` (latest stable per registry, EOL via endoflife.date, deprecation, abandonment, and the successor project where one is named), `stack-gaps` (what should be here and is not), `stack-fitness` (redundancy, over- and under-engineering, orphaned dependencies, ghost services, expired rationale), `stack-proposal` (target state, sequenced work items, execution brief), `stack-diff` (what changed since the last run). `/stack-eval` runs the sequence. The stack is described against a **fixed list of ~50 slots** rather than freehand, because a freehand description only ever lists what exists whereas a slot list also shows what does not — absence is the finding this plugin exists to surface. Expectations are **archetype-relative**: a static site needs no queue, an authenticated API with no rate limiting is real, and the archetype (`web-app` / `api-service` / `data-pipeline` / `mcp-server` / `homelab-service` / …) is recorded so a *changed* archetype is itself flagged. **Caching is asked about explicitly at all five layers** — edge/CDN, HTTP response, application, data access, client — separately from the archetype table, since it is the slot most often silently absent; but it is only reported as a gap where there is evidence of something worth caching (repeated identical queries, a paid API in a hot path, idempotent LLM inference with no memoization), because adding a cache to an unloaded system buys a new failure mode and a new consistency problem with nothing. Recommendations are right-sized to the project, not to a reference architecture: Postgres `SELECT … FOR UPDATE SKIP LOCKED` before Kafka, an in-process TTL map before Redis, one compose file before Kubernetes, with the heavier option noted as the upgrade path and the signal that would justify it. Being behind is **not** automatically a defect — a supported component two minors back gets a passing grade and one line; findings are reserved for past-EOL, EOL within 12 months, deprecated-with-successor, abandoned, unpatched, or actually blocking something. State persists in the evaluated repo at `docs/stack/stack.json`, which carries three things between runs and is the reason a second evaluation is worth more than a repeat of the first: **settled decisions** (a slot marked `intentionally-absent` with a reason and a date is never re-raised), **finding age** (`first_seen` is never reset, so something open across four runs reads as chronic rather than new), and **rejections**. `stack-diff` also re-checks whether stated reasons have quietly expired — "no production data yet" against a repo that has since grown a deploy target. Evaluation and execution stay separate: nothing in the plugin changes a stack, and the `execution-brief-<date>.md` it hands off copies its work items in rather than referencing them, authorises exactly what it lists, and requires a verification step and rollback path per item — so an implementing agent does not read "stack review" as licence to modernize everything it sees. Not a code reviewer, security scanner, vulnerability database or profiler. Listed under Repo Scaffolding & Retrofitting.
